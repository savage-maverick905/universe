# Universe: Data Model

Status labels: Implemented / Planned. Last updated: Phase 6. Not yet built: media for apps other than Inventory.

All data lives in the storage interface (`database/storage.js`) as JSON documents in named collections. Every document has a string `id`, `createdAt`, `updatedAt`. Ids are prefixed (`user_`, `item_`, `cat_`, `loc_`, `aud_`).

## Core collections (Implemented)
| Collection | Purpose | Key fields |
|---|---|---|
| `users` | accounts | email, displayName, passwordHash (scrypt), roleId, status (active/disabled), grants[], denies[], profile{avatarUrl,bio}, profileVisibility{field:{level,sharedWith}} |
| `roles` | named permission sets | name, permissions[] (`*`, `app.*`, exact), system, locked |
| `sessions` | logins | id = SHA-256 of the cookie token, userId, expiresAt |
| `app_installations` | which apps are installed | id = app id, version, enabled, installedBy, installedAt |
| `audit_log` | sensitive actions | at, actorId, action, targetType, targetId, outcome, meta (secrets redacted), ip |

## AI collections (Implemented)
`ai_profiles` (id = userId; name, instructions, style, preferences, keyMode, provider, model, encryptedKey, keyLast4), `ai_conversations` (userId, title, messageCount), `ai_messages` (conversationId, userId, seq, role, content, toolCalls, toolName, provider, model, usage), `ai_usage` (shared-key counters per user per day), and `settings` (document `ai` holds admin defaults: defaultProvider, defaultModel, sharedKeyEnabled, sharedDailyLimit). Details and rules in `docs/AI_ARCHITECTURE.md`. Provider configuration for users lives in `ai_profiles`; the owner's key is an environment variable, not data.

## Reports (Implemented)
`reports` collection: saved report results. `{id, userId, title, request:{report,period}, result:{title,range,filters,generatedAt,sections[]}, createdAt}`. Owner-only; newest 50 per user are kept. Report definitions themselves are not stored: they come from app manifests (`reports`) and the handlers apps register at startup. See `docs/ARCHITECTURE.md` section 8 for the section format.

Permissions are not stored as a collection: they are declared in app manifests (plus core ones in `auth/permissions.js`) and referenced by string.
Applications are not stored either: they are discovered from `apps/*/manifest.json`; only the installation state is data.

## Inventory (Implemented)
Collections owned by the app (prefix `inventory_`, declared in its manifest): `inventory_items`, `inventory_categories`, `inventory_locations`, `inventory_settings`.

Item (`schemaVersion: 1`), as stored:
```
id, schemaVersion, archived, createdAt, updatedAt
identity      { name*, description, categoryId|null, tags[] }
ownership     { type: "personal", ownerId }          server-set, never client-supplied
status        { state, reason }                      state in: in_use not_in_use lost lent_out given_away sold damaged under_repair disposed stolen
location      { type: home|work|storage|with_someone|other, locationId|null }
acquisition   { method|null, date|null, source|null, price|null, currency|null }
condition     { state: new|good|fair|poor|broken, notes }
identification{ brand, model, modelNumber, serialNumber, imei }   all nullable
media         { images[{publicId,secureUrl,resourceType,width,height,format,uploadedAt}], documents[] }   documents unused so far
relationships { parentItemId|null, relatedItems[] }
history[]     { date, event, reason, from?, to? }    events: created, status_changed, moved, condition_changed, note, archived, restored, imported
notes
```
Differences from the original spec sketch: `componentOf` was dropped (duplicate of `parentItemId`); `archived` and timestamps were added; ids are generated by the server.

Category: `{id, ownerId, name, icon}`. Location: `{id, ownerId, name, parentId|null}` (a tree, loops rejected). Both are per-user. Each user gets six default categories on first visit (`inventory_settings` marks that it happened).

### Rules
- **Ownership and isolation:** every record carries its owner. Every query filters by the session user; other users' records answer 404. Admins do not see other users' inventory. Sharing items between users is Planned.
- **References** (category, location, parent, related) must exist and belong to the same user. Deleting an item removes references to it. Categories/locations in use cannot be deleted.
- **Status and history:** status, location and condition changes append history automatically. History keeps the last 500 entries.
- **Delete:** archive first (reversible), then permanent delete.
- **Media:** only Cloudinary metadata is stored, and `secureUrl` must be an https `res.cloudinary.com/<your cloud>/` URL. The browser uploads directly to Cloudinary; no image bytes touch this server.
- **Schema versioning:** `schemaVersion` on items and on export files. When the shape changes, bump it and add a migration in `database/migrations/` (migration runner is Planned; none needed yet).

## Modularity
An app only touches its own `<appid>_*` collections and exposes data to the rest of the ecosystem through manifest-declared widgets, AI tools and reports, all served by permission-checked endpoints under `/api/apps/<appid>/`. No app reads another app's collections directly.

## Export / import (Implemented)
- System level: `npm run export -- file.json` and `npm run import -- file.json [--replace]` (wrap `storage.exportAll()` / `importAll()`; all collections except sessions; the file contains password hashes and encrypted API keys, so keep it secret; merge mode upserts by id). For migrating or backing up the whole ecosystem; tested with a real database round trip.
- Inventory, per user: `GET /api/apps/inventory/export` and `POST /api/apps/inventory/import` (limits: 2000 items, 500 categories, 500 locations, 5 MB). Import validates every record like a normal save, assigns **new ids** owned by the importer (it can never overwrite anyone's data), and remaps references. It always adds; it does not merge or deduplicate. Documents with unknown fields are rejected.
